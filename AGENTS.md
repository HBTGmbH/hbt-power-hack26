# AGENTS.md

HBT Power is HBT's skills/profile management app: a React webclient plus six Spring Boot services, each a standalone project in its own top-level `pwr-*` folder ([ADR-01](docs/arc42/09-architekturentscheidungen.md#adr-01-monorepo-mit-eigenständigen-projekten-je-ordner)).

**One owner per content (documentation rule).** Every rule, command, fact and instruction is written down in exactly one place, its owner; every other place links to it (relative link, with the section) and says at most in half a sentence what is found there, never repeats or paraphrases it. A change goes to the owner only; whoever finds a copy replaces it with a link. The owners:

- **This file:** the binding rules for working on the code, each with at most one sentence of context, the Definition of Ready and the Definition of Done; the commands an agent needs while working: build and test, the pre-commit hook, `JAVA_HOME` in a non-interactive shell.
- **[`README.md`](README.md):** installing the prerequisites, IDE setup, running locally (infrastructure, starting services and webclient, test data).
- **[`docs/arc42/`](docs/arc42/README.md):** how the architecture works and why (context, building blocks, flows, concepts, risks), linking to the rule here instead of restating it; the decisions as ADRs in chapter 9; deployment and operation facts (memory limits, volumes, production configuration) in chapter 7.
- **[`docs/glossar/`](docs/glossar/):** the meaning of a term. `docs/arc42/12-glossar.md` is generated from it and the only allowed copy.
- **`pwr-*/README.md`:** only what the service does in a few lines, linking to the owners (#253).
- **`.claude/skills/*/SKILL.md`:** how the skill works. A skill carries out a rule, it doesn't restate it: it links to the rule and only adds the steps.

## Build and test

All Java services need **JDK 13**, the webclient Node 20 ([`README.md` › Prerequisites](README.md#prerequisites)). `./mvnw` uses `JAVA_HOME`; in a non-interactive shell run `eval "$(jenv init -)"` first, otherwise `export JAVA_HOME=$(/usr/libexec/java_home -v 13)`.

```shell
cd pwr-<name>-service
./mvnw package                                   # build + all tests (what CI runs: ./mvnw -B package)
./mvnw test -Dtest=ClassName                     # single test class
./mvnw test -Dtest=ClassName#method              # single test method
```

All services share one script-only Maven wrapper (Maven 3.9, `distributionType=only-script`, no `maven-wrapper.jar` in Git) that checks the SHA-256 of the Maven download; update it in one service with `./mvnw wrapper:wrapper -Dmaven=<version> -Dtype=only-script`, add `distributionSha256Sum`, and copy `mvnw`, `mvnw.cmd` and `.mvn/wrapper/maven-wrapper.properties` to the others. Keep `mvnw` executable in Git (`git update-index --chmod=+x`). The POMs follow the same conventions: groupId `de.hbt.pwr`, version `1.0.0` (see *Commit instead of version*), `<finalName>${project.artifactId}</finalName>` (so the jar is `target/<service>.jar`, which the Dockerfile copies), no extra repositories besides Maven Central, Java level only through `java.version`, Lombok `optional` with the version of the Boot parent and excluded from the jar in the `spring-boot-maven-plugin`, and no explicit version for what the Boot parent manages.

Tests need no running infrastructure ([arc42 8.9](docs/arc42/08-querschnittliche-konzepte.md#89-build-stand-und-tests)). In the statistics service, tests tagged `heap-limit` (`SimRankHeapLimitTest`, #292) run in a second surefire execution with `-Xmx64m`, so SimRank stays small; `-Dtest=` works for both.

Webclient (`pwr-webclient`, CRA/react-scripts, TypeScript). Env vars in npm scripts go through `cross-env` so they work on Windows:

```shell
npm --prefix pwr-webclient install
npm --prefix pwr-webclient run build
```

Running it: [`README.md` › Start the webclient](README.md#3-start-the-webclient). Screenshots of any page with mocked data, and recording fixtures: the skill [`ui-screenshot`](.claude/skills/ui-screenshot/SKILL.md).

The pre-commit hook in `.githooks/pre-commit` tests every `pwr-*` package that has staged changes. A service runs `./mvnw -B -q test`; the webclient runs the TypeScript check `tsc --noEmit`. Turn the hook on once per clone with `git config core.hooksPath .githooks`. A failing test blocks the commit. `git commit --no-verify` skips the hook, and CI still runs the full build.

## Architecture

How it works and why: services, ports, storage and calls in [arc42 5](docs/arc42/05-bausteinsicht.md), flows in [6](docs/arc42/06-laufzeitsicht.md), the concepts behind the rules below in [8](docs/arc42/08-querschnittliche-konzepte.md), decisions in [9](docs/arc42/09-architekturentscheidungen.md).

- **Authentication lives only in the edge, the check per consultant in each service** (#255, [ADR-04](docs/arc42/09-architekturentscheidungen.md#adr-04-anmeldung-und-rollen-nur-in-der-edge-identität-über-header)): the backend services get no authentication and no Spring Security of their own until they check tokens themselves ([ADR-24](docs/arc42/09-architekturentscheidungen.md#adr-24-spring-security-in-den-backend-services-erst-mit-eigener-tokenprüfung)). **Rule for the whole app:** the services read the logged-in user only from the headers `X-Pwr-User-Login`, `X-Pwr-User-Initials` and `X-Pwr-User-Admin`, which the edge sets from the verified token, never from a request body, a path or a query parameter, not even in a call between services: a service that calls another passes the login and initials on (#214). Initials in a path say which profile a request is about, not who is logged in. How the edge checks and sets them: [arc42 8.1](docs/arc42/08-querschnittliche-konzepte.md#81-sicherheit).
- **Admin paths have two layers** (#260): the edge rejects every path that is not normalized (`NormalizedPathFilter`), and every service with `/admin` endpoints answers `403` there itself when `X-Pwr-User-Admin` is `false` (`AdminAccessInterceptor`, by the mapping Spring MVC chose, not the text of the path). Why: [arc42 8.1](docs/arc42/08-querschnittliche-konzepte.md#81-sicherheit).
- **A user reads and changes only the own data, an admin everyone's** (#255); **the profiles of the colleagues every consultant reads** (#350), nothing else of them (no birth date, profile check, view profiles, documents or profile statistics). Profile, report, view-profile and statistics service check it themselves (`security/ConsultantAccess`, how: [arc42 8.1](docs/arc42/08-querschnittliche-konzepte.md#81-sicherheit)). So: name the consultant a path is about `{initials}`; check the owner of anything loaded by an id with `ConsultantAccess.check(owner)` where it is loaded; an id in a body must belong to the profile in the path, for admins too (`ProfileEntryService.requireInProfile`, `ViewProfileOperationService.isOwner`); mark what colleagues may read with `@ReadableByColleagues`, on GET mappings only (`ConsultantAccessITest`), a new endpoint stays with the consultant unless marked; put personal data about others that only the admin area needs under `/admin`. A whole profile is only read (`GET /profiles/{initials}`), never replaced from a body (#261). Documents only come from the view-profile service (#262). The webclient opens the profile of a colleague only to read (`OIDCService.mayEditProfile`, `isProfileReadOnly`).
- **Skill tree changes are admin-only** (#178): everything that creates, moves, deletes or localizes skills and categories, deletes versions or rebuilds the index lives under `/admin/skill/**` and `/admin/category/**` of the skill service (`SkillAdminController`, `CategoryAdminController`). Outside `/admin` there are only reads plus what a consultant does while editing a profile: `POST /skill?qualifier=` puts an unknown skill into "Other", `POST /skill/{id}/version` adds a version.
- **Report templates are admin-only** (#203): uploading, changing and deleting them lives under `/admin/template` of the view-profile service (`ReportTemplateAdminController`), their files under `/admin/file` of the report service. Outside `/admin` there are only reads (`GET /template`).
- **Managing consultants is admin-only** (#218): listing, creating, changing and deleting consultants and the consultant selection live under `/admin/consultants` of the profile service (`ConsultantAdminEndpoint`). Outside `/admin` there are only `GET /consultants/{initials}` (the own profile) and `GET /consultants/names` (#216). Deleting a consultant deletes everything about the consultant in every service (#240, [arc42 6.7](docs/arc42/06-laufzeitsicht.md#67-berater-löschen-admin)).
- **Housekeeping** (#242, #288, #289, [ADR-21](docs/arc42/09-architekturentscheidungen.md#adr-21-housekeeping-je-service)): every service reports and cleans the inconsistencies of the data it stores itself; what it needs from another service it only reads there, it never deletes there. If that service doesn't answer, or answers with no consultant at all, the check reports an error instead of findings; an empty usage is never a reason to delete. *Unbenutzt* and *Alt* are decisions of the admin, no repair: the newest of each consultant always stays, and only skills of the category *Other* can be unused own skills (the flag `custom` tells nothing, #297). Checks, rubrics and endpoints: [arc42 8.3](docs/arc42/08-querschnittliche-konzepte.md#83-konsistenz-über-services). **Rule:** whoever adds a reference across services or a delete that is not transactional adds a check to the service that stores the data.
- **Service-to-service calls use `RestTemplate`** ([ADR-03](docs/arc42/09-architekturentscheidungen.md#adr-03-aufrufe-zwischen-services-mit-resttemplate), base URLs and timeouts: [arc42 8.4](docs/arc42/08-querschnittliche-konzepte.md#84-kommunikation-zwischen-services)). Every client gets its `RestTemplate` from the `RestClientConfig` of its service, never `new RestTemplate()` (#249), calls known to take longer the `slowRestTemplate` (`@Qualifier(RestClientConfig.SLOW)`). Free text in a query parameter (names of skills, profile elements) goes through `UriComponentsBuilder…queryParam(name, "{name}").encode().buildAndExpand(value)`, never into a URL template string: `RestTemplate` leaves `+` in a template unencoded, and the receiving service reads it as a space (`C++`, #330).
- **The internal note of a project** (`Project.internalNote`, #336) stays in the profile service: the view-profile, report and statistics services read profiles but don't map it, so keep it out of their models.
- **Statistics** answer from their own copy of all consultants and profiles ([ADR-10](docs/arc42/09-architekturentscheidungen.md#adr-10-statistik-mit-eigener-kopie-aller-berater), [arc42 6.5](docs/arc42/06-laufzeitsicht.md#65-statistik-aktuell-halten)). A change of many profiles at once (merging, renaming and deleting skills and profile elements, deleting a consultant) lets the profile service reload the copy after the commit (`StatisticsClient.refreshConsultantsAfterCommit`), and the webclient drops the cached usage of skills and profile elements (`statisticsReducer.skillUsageInfo`, `nameEntityUsageInfo`).
- **Schema management:** no Liquibase/Flyway ([ADR-08](docs/arc42/09-architekturentscheidungen.md#adr-08-schema-mit-hibernate-ddl-auto-update-ohne-migrationswerkzeug)); Hibernate (`ddl-auto: update`, in production too) only adds tables and columns. It never drops, renames or changes a column, a type or data, so such changes need hand-written SQL for production (see `pwr-profile-service/fix-id-columns.sql`).
- **Commit instead of version** (#77, [ADR-06](docs/arc42/09-architekturentscheidungen.md#adr-06-commit-statt-version)): the versions in `pom.xml` and `package.json` are not maintained (no `SNAPSHOT`; every POM says `1.0.0`). Every service publishes its commit at `GET /actuator/info` (`git.commit` from the `git-commit-id-maven-plugin`, only branch, commit id and time; no `build-info`), the webclient in `build_info.json` (`compileBuildInfo.js`). Only `health` and `info` are published.
- **Memory** (#293): every Dockerfile sets a heap limit and `G1PeriodicGCInterval` in `JAVA_TOOL_OPTIONS` (values, measurement, overriding: [arc42 7.5](docs/arc42/07-verteilungssicht.md#75-speicher-der-java-services)). Whoever makes a service need much more memory measures again and adjusts its limit.
- **Fonts in PDFs** (`PdfFonts`, report service): the HBT font Simplon Norm is licensed and must never be committed or baked into an image; production mounts its files at `/fonts` (`export.font-directory`). Stand-in, mapping and embedding: [ADR-12](docs/arc42/09-architekturentscheidungen.md#adr-12-lizenzierte-schrift-nie-im-repository-oder-image).
- **Localizations** of skills and categories (`LocalizedQualifier`, #174) and of profile elements (`NameEntityLocalization`, #291) are only shown when a view profile has a language (`ViewProfile.localization`). The name of the skill tree or of the profile element stays the key everywhere, the translation goes into `localizedName` next to it (`localizedClient`/`localizedBroker` of projects), and only the report replaces the name with it. `localizedName` is no part of `equals`, so *Aktualisieren* matches entries as before. How: [arc42 8.6](docs/arc42/08-querschnittliche-konzepte.md#86-lokalisierung-und-datum).
- **Names compare ignoring case** (#207): the MariaDB collation ignores case and accents ([arc42 2.1](docs/arc42/02-randbedingungen.md#21-technische-randbedingungen)), so name comparisons in Java that decide the same thing need `equalsIgnoreCase`. The tests run H2 with `IGNORECASE=TRUE` to behave alike (accents are not covered). H2 accepts `in ()` for an empty list, MariaDB rejects it, so guard every `in :list` against an empty list. A test of a delete flushes (`entityManager.flush()`), otherwise the rollback of the test hides a violated foreign key (#243). Names of profile elements are saved without spaces at the ends, and a blank name never becomes one (#215): a profile entry without a name is rejected with `400`, an emptied client, broker or role is none.
- **Skill names are normalized to the skill tree** (#208, [ADR-13](docs/arc42/09-architekturentscheidungen.md#adr-13-skill-namen-aliase-normalisierung-auf-den-baum-groß-kleinschreibung)): a skill name in any case or an alias stands for the name of the skill in the tree; names the tree doesn't know stay. Saving a new skill only takes over the spelling of the tree (`.net` → `.NET`); **aliases stay as typed** in the profile. Everything that reads profiles uses the tree name, and skills that end up with the same name in one profile or project become one with the higher rating. Where each service normalizes: [arc42 8.5](docs/arc42/08-querschnittliche-konzepte.md#85-namen-und-stammdaten).
- **Renaming, merging and deleting across all profiles** (#227–#230), all under `/admin` of the profile service (flows in [arc42 6.6](docs/arc42/06-laufzeitsicht.md#66-einen-skill-in-allen-profilen-umbenennen-admin), names and aliases in [8.5](docs/arc42/08-querschnittliche-konzepte.md#85-namen-und-stammdaten)):
  - Profile elements (`NameEntity`, `NameEntityAdminEndpoint`): the former names of an element and the aliases admins add (#270) are unique within the type of element, ignoring case, and no other element of the type has one as name; renaming to the alias of another element is a conflict (409).
  - Skills are first changed in the skill tree, then in the profiles and projects. Merging stays #205.
  - View profiles stay snapshots; only *Aktualisieren* takes changes over (#332).
  - Hibernate: the hash of a `ProfileEntry` depends on its `NameEntity`, so after repointing entries the profile's set is rebuilt before removing from it, or Hibernate detaches the kept ones. Nothing that leaves a profile stays behind as a row (#254); skills, which the projects of the profile hold too (no orphan removal on `Profile.skills`), are taken out of the profile and its projects and deleted through `SkillRows`. `NoLeftoversITest` checks every such path against the housekeeping checks; a new one belongs there. Old data still has such rows: count usage only through joins from `Profile`, and delete those rows together with the element. Old data also has rows in `profile_entry` without a row in the table of an entry type (#236): load entries per entry type (`select e from SectorEntry e …`), never `from ProfileEntry`, and remove what is left with native SQL.
- **Skill search** ([ADR-14](docs/arc42/09-architekturentscheidungen.md#adr-14-skill-suche-mit-hibernate-search-und-lucene)): search and suggestions read only the Lucene index, never the database, and each call takes an `EntityManager` of its own: one shared by all requests broke the suggestions as soon as two ran at the same time (#352).
- **Spring profile syntax differs by Boot version:** 2.2 services use `spring.profiles: localDev` in multi-document YAML, the 2.7 services (edge, statistics) use `spring.config.activate.on-profile`.
- Java packages: one base `de.hbt.power` with a sub-package per service (`de.hbt.power.profile`, `.skill`, `.report`, `.edge`), so the services can be merged without clashing class names (HBTGmbH/hbt-power-hack26#17, HBTGmbH/hbt-power#50). View-profile (`de.hbt.pwr.view`) and statistics (`de.hbt.pwr`) keep theirs for now: Spring Data Redis stores the full class name with the data, so renaming their models needs a migration of the stored data first.

### Webclient

- Redux state in `src/reducers`, components in `src/modules` (`admin`, `home` = profile editing, `general` = shared components).
- Navigation: both areas have a menu behind the burger in the app bar (`PowerToolbar`, `AdminMenu`, #212). What is selected on a page is in its URL (#182, `Paths`, built with `Paths.build`), so reload and back work: the id selects, a slug of the name after it (`StringUtils.slug`) is only for reading; names that are no ids (used skills) go into a query parameter.
- Backend access goes through the axios wrappers in `src/clients` (`XyzServiceClient.instance()`), which count the running requests, extract the payload, show errors and re-throw them. A failure getting the token (`OIDCService.getToken`) ends the request with an error and never logs out (#311); only the menu logs out (new login during work: [arc42 6.1](docs/arc42/06-laufzeitsicht.md#61-anmeldung-und-ein-aufruf)). Requests run in the background (#320): no spinner in the middle of the page; every request counts in `crossCutting.pendingRequests` (`PowerHttpClient.counted`), shown as a thin bar along the app bar (`PwrRequestProgress`). The state changes only with the answer of the server; after an error it stays as it was, and the client's message is the only one (no second alert in the action creator, `.catch` only logs). Success messages only where the result can't be seen on the page; small saves (entries, skills, ratings, projects, view profiles) report none. Changes that save right away without a form (the stars of a skill, switching, moving and sorting on the view profile page) go through `saveInOrder` (`utils/SaveQueue.ts`): one after the other per queue, of several changes with the same key in a row waiting only the last one is sent, so the server and the page end at the last click. The queue is what the server saves as a whole: one per profile skill, one per view profile. The stars show a clicked rating faded until the answer (`StarRating` `pending`). `dispatch` of a thunk doesn't return its promise (`AsyncActionUnWrapper`): a component that needs the result passes a callback to the action creator.
- Binary content (profile pictures, report previews) is loaded through these clients as a blob and shown through a blob URL, never as `src`/iframe URL pointing at the API: those requests carry no token and the edge rejects them. Profile pictures go through `PwrProfilePicture` (`modules/general`), which caches them per picture id.
- New version (#247, [arc42 8.8](docs/arc42/08-querschnittliche-konzepte.md#88-bedienoberfläche)): `PwrNewVersionNotice` never reloads by itself: **Neu laden** asks about unsaved changes first (`confirmLeavingUnsavedChanges`).
- Static files: images, CSS and data live in `src/` and are imported, so the build serves them with a content hash under `/static/` ([caching: arc42 8.8](docs/arc42/08-querschnittliche-konzepte.md#88-bedienoberfläche)). `public/` only holds `index.html` and `favicon.png`.
- Dates without time (#26, [ADR-16](docs/arc42/09-architekturentscheidungen.md#adr-16-localdate-als-string-im-webclient)): every `LocalDate` field of the services (profile entries, birth date, view profile) stays the string `"YYYY-MM-DD"` (`LocalDate` in `utils/DateUtil.ts`) in models and Redux state. Only `PwrDatePicker` converts it to a `Date`, so no `new Date("YYYY-MM-DD")` or `toISOString()`. Timestamps (`LocalDateTime`) remain `Date`.
- Names of colleagues (#216, [ADR-15](docs/arc42/09-architekturentscheidungen.md#adr-15-kurznamen-der-berater-zentral-berechnet)): the app names consultants by their [Kurzname](docs/glossar/Kurzname.md), computed only by the profile service and loaded into `consultantNames` ([arc42 8.5](docs/arc42/08-querschnittliche-konzepte.md#85-namen-und-stammdaten)). Show it through `PwrConsultantName` (`modules/general`) and sort lists of consultants with `compareNames` (short name, full name on a tie, #277). The full name stays in export documents, the delete confirmation and the edit fields; the title of a consultant is the job title and belongs to neither name.
- Own profile: unknown initials of the logged-in account get a message, not an error (`ConsultantClient.findConsultant`; login and start page: [arc42 6.1](docs/arc42/06-laufzeitsicht.md#61-anmeldung-und-ein-aufruf)).
- Profile check (#139): the profile service computes it ([arc42 5.2.2](docs/arc42/05-bausteinsicht.md#522-pwr-profile-service)). A hint links to where it is fixed, through the anchors of the sections of the profile page (`#profile-section-<SECTION>`).
- Unsaved changes in a project: `PWR_HISTORY.block` (registered in `index.tsx`) holds back every navigation and asks through the `UnsavedChangesDialog`. Actions that leave a project without navigating (select another project, add a project, admin area, logout) go through `confirmLeavingUnsavedChanges` (`reducers/navigation/UnsavedChanges.ts`). Saving, cancelling and deleting don't ask.
- Colours (#201): errors and destructive actions in `palette.error` (red), warnings that are no errors (outdated, can't be undone) in `palette.warning` (dark orange), both in `PowerTheme.ts`. The HBT orange (`PWR_ACCENT`) is an accent only: a bar, a border, or an area with dark blue text on it; never the colour of text and never behind white text (2.3:1 on white). Text needs a contrast of 4.5:1, icons and other graphics that carry meaning 3:1. No colour names or hex values for text: Material-UI components take the theme (`color="error"`), `makeStyles` reads `theme.palette`, `index.css` uses the CSS variables `--pwr-error`, `--pwr-warning` and `--pwr-accent`, which `PwrThemeColors` sets from the theme.
- Input fields use the Material-UI `filled` variant (grey area), set as default in `PowerTheme.ts`: don't set `variant` per field. Components the theme doesn't reach (`ChipInput`, `FormControl` around a `Select`) get `variant="filled"` explicitly. Disabled and read-only fields have no grey area, so read mode looks different from edit mode.
- Form spacing on the 8 px grid of `theme.spacing` (`modules/general`): `PwrSpacer` with `tight` (8 px: label and value, chips, one row), `field` (16 px, default: between the fields of a group) and `section` (32 px: between sections, before the button bar). A group with a heading is a `PwrFormSection` (section space above), chips or small buttons in a row a `PwrRow`. No inline margins and no single classes for spacing in forms.
- Lists and small tables: `PwrListTable` (`modules/general`, #199), in the look of the view profile tables (#149): grey header row of 12 px, rows of 14 px and at least 40 px with a line between them. With `onSelect` the rows are buttons (arrow keys move between them) and the selected one is highlighted. A column with `sortValue` sorts by a click on its header (#342; texts like names, numbers by value, `undefined` last), `initialSort` names the order the items come in.
- Form buttons: `PwrFormActions`. The main action with text and highlighted (`Bearbeiten` in read mode, `Speichern` in edit mode), `Abbrechen` as a text button next to it, `Löschen` set apart on the right in the error colour. Dialogs with a form use it too, inside `DialogActions` (`noSpace`, own label and icon for the main action, e.g. `Erstellen`). Further actions go between the main action and `Abbrechen` (`Zurück` in a wizard). A project reference has no read mode (#338): it opens editable, with `Speichern` and `Änderungen verwerfen` (`cancelText`) active only once something changed (`selectedProjectHasChanged`; a new project can always be discarded), and its URL has no `/edit` (old links lead to the project). Confirmation dialogs use `PwrConfirmActions`: the confirming action highlighted, in the error colour if it destroys something (`Löschen`, `Änderungen verwerfen`), the rejecting one as a text button. Every delete asks first: through `makeDeferrable` with its own `ActionType`, registered in `DeferredActionMiddleware`. In the admin area (#181) the question is not enough: the action creator passes `confirmByName` to `makeDeferrable` (built with `confirmDeleteByName`), the dialog names the entry and what goes with it, and `Löschen` only becomes active once the name (initials for a consultant, the translation for a localization, the version) was entered twice, exactly as written apart from spaces at the ends. In lists (profile entries, projects, export documents, view profiles) delete is a trash icon per entry, not a button of the form; the view profiles (#213) are a `PwrListTable` with icon buttons for `Generieren`, `Bearbeiten` and `Löschen` per row, the newest three on the overview and all under `/app/<initials>/views`.

## CI

One GitHub Actions workflow per folder (`.github/workflows/<folder>.yml`), path-filtered (the same filter for `push` and `pull_request` via a YAML anchor). Each has two jobs:

- **`check`** ("Build and test") on pull requests against `main`: build with Zulu JDK 13 / Node 20, run tests, build the image without pushing. Read-only token, dependency caches allowed.
- **`publish`** on push to `main` (or manually): the same build, then push the image to `ghcr.io/hbtgmbh/hbt-power/<folder>`. Only this job has `packages: write`, and it uses no dependency cache, so nothing cached by a PR run can end up in an image. During the hackathon it only runs in the upstream repository `HBTGmbH/hbt-power` (`github.repository` in its `if`), so this fork publishes no images.

Workflow changes must pass actionlint and zizmor ([arc42 7.2](docs/arc42/07-verteilungssicht.md#72-vom-merge-in-die-produktion), [ADR-18](docs/arc42/09-architekturentscheidungen.md#adr-18-ci-je-ordner-mit-pfadfiltern-und-getrenntem-publish)).

- **`lint-actions.yml`** ("Lint GitHub Actions") runs on every PR against `main` and every push to `main` that touches `.github/**`: actionlint with shellcheck and zizmor (online audits), with `contents: read` only. Locally: `uvx --from actionlint-py --with shellcheck-py actionlint` and `uvx zizmor --persona regular .` from the repository root.
- **Pinning policy** in `.github/zizmor.yml`: first-party actions (`actions/*`, `github/*`, `docker/*` …) and `HBTGmbH/*` with a major tag (`@v7`), all others with the full commit SHA plus a `# vX.Y.Z` comment.
- **Dependabot** (`.github/dependabot.yml`) opens a PR for new action versions once a week, at the earliest 7 days after a release (`cooldown`). For a new major version check that every input the workflow uses still exists in the new `action.yml`. Maven and npm are not covered.

## Knowledge base

The project knowledge (public docs, an optional private **project sidecar** readable by project members only, and optional **HBT-wide knowledge** readable by all employees, [ADR-26](docs/arc42/09-architekturentscheidungen.md#adr-26-wissensbasis-aus-öffentlicher-doku-und-privatem-sidecar)) is searchable through the MCP server `knowledge` (installation and tools: [`README.md` › Knowledge base](README.md#knowledge-base)).

The knowledge base is being tried out (ADR-26, status *vorgeschlagen*). While that trial runs, the rules below and the knowledge-base item of the Definition of Done apply to everyone who works with it; if ADR-26 is rejected, they go with it. The domain language (ADR-27) applies regardless.

- The weekly run changes only Markdown; outdated code comments it finds are listed as hints in the project sidecar (`consolidation/hints.md`), shown by `status` and at the start of each session. Working in that area, fix the comment in the same branch as a small fix along the way and delete the hint from the sidecar file.
- Look things up before answering questions about the domain, processes, terms, architecture or decisions, and before changing code whose business meaning is unclear. Cite the `id` of the source.
- **Decisions** form one register: public ADRs (arc42 chapter 9) and internal ones (`ADR-Inn` project, `ADR-HBT-nn` HBT-wide). Check `decisions <topic>` before changing architecture, flows or rules; record new ones with `decide` (scope `public`, `intern` or `hbt`). Superseded decisions stay, marked „abgelöst durch ADR-nn“.
- The glossary is the binding **domain language**: one term per thing. Name things in docs, UI texts, comments and new code with the glossary term or its code name; replace words listed under „Nicht verwenden“ (`define <word>` tells you the right term). Add a new term to the glossary before using it. Each term is a note (`docs/glossar/<Term>.md`); link it with a normal relative Markdown link (no `[[…]]` wikilinks in this repository — they belong to the private Obsidian knowledge modules only); `audit` reports deviations.
- Results marked **INTERN** (project sidecar) or **INTERN:HBT** (HBT-wide) are private: use them to understand, never copy them, literally or paraphrased, into code, comments, test data, commits, issues, PRs or public docs, and never copy project knowledge into HBT-wide knowledge. A hook blocks literal copies; `check` scans the repository.
- New knowledge goes where it belongs: public (arc42, glossary, this file) for architecture, code and UI terms; the project sidecar for internal processes, customers, sales and operations of this project (when in doubt, here); HBT-wide knowledge only for what applies to all projects and reveals nothing about this one.

## GitHub workflow

- **Repository:** `HBTGmbH/hbt-power` (take the owner from `git remote get-url origin`). It is **public**.
- **Hackathon fork:** this checkout (`HBTGmbH/hbt-power-hack26`) is a fork of [`HBTGmbH/hbt-power`](https://github.com/HBTGmbH/hbt-power). Issue numbers in the code and docs (`#NNN`, e.g. the open ones in `docs/arc42/11-risiken-und-technische-schulden.md`) refer to the upstream repository: look them up with `gh issue view NNN --repo HBTGmbH/hbt-power` and link them as `HBTGmbH/hbt-power#NNN`.
- **No operating environment details on GitHub:** no host names, deployment or management URLs, tenant/client IDs, connection strings, secrets, or queries against live systems in issues, PRs, commit messages, code, comments, docs or screenshots. Write „the production environment“, `<host>` instead. A later edit doesn't help: GitHub keeps the edit history and git keeps the commit.
- **Issue structure:** as required by the [Definition of Ready](#definition-of-ready); the skill [`new-issue`](.claude/skills/new-issue/SKILL.md) writes and checks one.
- **Issue type:** set after creation via GraphQL: `Task` `IT_kwDOAYn5ks4AV-6C`, `Bug` `IT_kwDOAYn5ks4AV-6D`, `Feature` `IT_kwDOAYn5ks4AV-6H`.
  ```bash
  gh api graphql -f query='mutation { updateIssue(input: { id: "<node_id>", issueTypeId: "<type_id>" }) { issue { number issueType { name } } } }'
  # node_id: gh api repos/HBTGmbH/hbt-power/issues/NNN --jq .node_id
  ```
- **Branches:** named and branched as the [Definition of Ready](#definition-of-ready) says: `feature/…` for a new capability, `bug/…` for a defect. One issue per branch and PR, no bundling, except for small fixes (next bullet). No direct pushes to `main`.
- **Small fixes along the way:** fix small defects you come across directly in the current branch, as long as they don't put the current ticket at risk. Small means: an obvious defect, a few lines, cause and fix clear without further analysis, no change to an API contract, entity, Redis model or the edge path rules, and verifiable within the current test and click-through. Commit it separately with the current issue ID (`#12 - Nebenbei: …`) and list it in the PR under *Beschreibung*. Anything bigger, or anything that would delay or blur the current ticket, gets its own issue.
- **Line endings:** LF for all text files, CRLF only for `*.cmd`/`*.bat`, set in `.gitattributes`. Commits that only reformat (like the normalization in #46) go into `.git-blame-ignore-revs`, so `git blame` and GitHub skip them (locally: `git config blame.ignoreRevsFile .git-blame-ignore-revs`).
- **Commit messages:** every commit starts with the issue ID, then ` - `, then a short description, e.g. `#12 - Skill-Suche ignoriert Groß-/Kleinschreibung`. Without an issue (typos, trivial housekeeping): `#noissue - …`.
- **Pull requests:** fill in [`.github/pull_request_template.md`](.github/pull_request_template.md), with `Closes #NNN` and its compliance sentence.

## Definition of Ready

Before writing any code:

- [ ] An issue exists and its type is set (`Bug`, `Feature`, `Task`) before the branch is created
- [ ] The issue says what is wrong or missing (*Ist-Zustand*), what must hold afterwards (*Wunsch*) and how to check it (acceptance criteria as a checklist), each thing once. It names the code it touches but repeats nothing the code, the docs or the Definition of Done already say
- [ ] It fixes the result and binding decisions, not the way there: no classes, annotations or APIs to use that no ADR prescribes
- [ ] Each criterion can be checked in the repository or the PR, or is marked *(Mensch)* when it needs production, and together they say when the issue is done
- [ ] A visible change has a mockup: a sketch in a code block or an image without real data. A ` ```mermaid ` diagram only where it shows more than the text
- [ ] The body has at most 12000 characters, or the issue is split: the software factory reads no more
- [ ] `main` is checked out and up to date: `git checkout main && git pull`
- [ ] A dedicated branch exists: `feature/<issue>-<short-description>` or `bug/<issue>-<short-description>`

## Definition of Done

Apply this at the end of each task to what the task changed, and report which items apply and whether each is satisfied. A task is done when all applicable items are true.

### Build and tests
- [ ] `./mvnw verify` passes in every changed `pwr-*-service` (JDK 13)
- [ ] `npm run build` passes if `pwr-webclient` changed
- [ ] All existing tests pass; new backend behaviour is covered by tests

### Services
- [ ] **API contracts:** if an endpoint changed, every caller is adjusted in the same PR: the `RestTemplate` clients in the other services and `pwr-webclient/src/clients`
- [ ] **Logged-in user:** whoever acts (creator, exporter, confirmer …) is read from `X-Pwr-User-Login`/`X-Pwr-User-Initials` only, never from a body, path or query parameter; calls between services pass these headers on
- [ ] **Edge security:** new or moved endpoints are checked against the path rules in `pwr-edge-service/.../filters/SecurityConfig.java`; admin functionality must live under a path the edge restricts to `Power.Admin`
- [ ] **Own data only** (#255): an endpoint about one consultant has the initials as path variable `{initials}`, or checks the owner of what it loads by an id with `ConsultantAccess.check`; a test shows `403` for another user and access for the owner and an admin
- [ ] **Redis compatibility:** changes to Redis models (`ViewProfile`, `ReportTemplate`, statistics models) keep existing stored data readable. Spring Data Redis stores an object as a hash with one entry per field, reads only the fields of the model and rewrites the whole hash on save. So renaming a field or changing its type needs a migration; removing one doesn't (the old entry is passed over and goes with the next save, #179); a new field is missing in old data and needs a default
- [ ] **Database schema:** a change Hibernate can't do (see *Schema management* under [Architecture](#architecture): rename, drop, type change, data migration) comes with a SQL script for production. Every schema change is listed under *Operations / Deployment Notes* in the PR

### Webclient (if UI changed)
- [ ] User-facing text goes through `PowerLocalizer`; new keys are in `src/localization/de-DE.json`
- [ ] Shared components from `modules/general` are reused: `PwrButton` / `PwrIconButton`, icon on the right, icon buttons with tooltip
- [ ] Backend access only through the clients in `src/clients`; enums use string values
- [ ] The change was clicked through with `npm run start:local` against the local backend

### Documentation and pull request
- [ ] `AGENTS.md` and `README.md` are updated in the same PR if a rule, command, port or prerequisite changed
- [ ] The affected chapter of [`docs/arc42/`](docs/arc42/README.md) is updated in the same PR if a service, an interface between services, a flow, the deployment or an architecture decision changed (a new decision gets the next ADR number in chapter 9)
- [ ] No operating environment details in code, docs, commits, issue or PR (see GitHub workflow)
- [ ] Nothing from the private knowledge sidecar in code, docs, commits, issue or PR: the MCP tool `check` with `staged: true` passes (see Knowledge base; applies while ADR-26 is being tried)
- [ ] Every commit message starts with `#NNN - ` (or `#noissue - `)
- [ ] Small fixes made along the way (see GitHub workflow) are listed in the PR
- [ ] PR body follows the template, contains `Closes #NNN` and the compliance sentence
- [ ] The fulfilled acceptance criteria are ticked off in the issue, a *(Mensch)* criterion only by a human. A criterion that is not fulfilled stays open, and the PR says why
